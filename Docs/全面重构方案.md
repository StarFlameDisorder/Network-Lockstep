# 全面重构方案（断线重连 + 网络层 + 架构简化）

> 创建于 2026-08-02
>
> 起因：用户反馈"断线重连有非常严重的问题，重连后客户端 UDP 连不上"、"部分逻辑与 UI 显示有问题"、"架构是 C++ 迁移来的旧架构，各方面不方便"。
>
> 目标场景：**网络瞬断后重连** + **客户端重启后重连** 两种都支持。
>
> 附加要求（用户 2026-08-02 补充）：
> 1. **连接状态一致性**：TCP 与 UDP/KCP 双通道状态必须同步（避免"TCP 断了 UDP 还显示连着"或反向），重要状态变化必须输出到 Debug.Log 与 UI 消息面板；
> 2. **大厅显示其他玩家加入房间**；
> 3. **支持中途加入**（游戏进行中，新玩家加入房间并恢复状态）。
>
> 原则：项目仅考虑"网络同步"一个核心目标，架构保持简单，不为假设需求过度设计。

## 一、断线重连根因分析（本次最严重问题）

用户症状：**客户端断线后重连，服务端显示该客户端的 UDP 始终连不上**。

### 根因 1：KCP 会话"懒创建"，重连快照被静默丢弃 ⭐核心

- 服务端 [KcpServer.ReceiveAsync](Assets/Scripts/Network/Server/KcpServer.cs#L84-L105) **只有收到某个 conv 的第一个 UDP 包时才创建 KcpSession**。
- 客户端重连流程：TCP 握手 → 拿到**新 clientId**（服务端 [HandleTcpConnected](Assets/Scripts/Network/Server/ServerNetworkDispatcher.cs#L119-L148) 分配）→ `SetClientId` 启动新 KCP → 发 JoinRoom。
- 服务端 `JoinRoom` 识别为重连后，**同步调用 [SendReconnectData](Assets/Scripts/Network/Server/RoomManager.cs#L363-L427) 立即通过 KCP 补发快照**。
- 此时服务端还没收到该 conv 的任何 UDP 包 → `_convToKcp` 无此会话 → `_kcpServer.Send` 走 [未知conv分支](Assets/Scripts/Network/Server/KcpServer.cs#L112-L120) → **快照+补帧全部丢弃**。
- 之后客户端心跳/游戏同步才让服务端创建会话，但**快照已经丢了** → 客户端永远拿不到快照，无法恢复世界状态。这就是"UDP 连不上"的直接表现。

### 根因 2：重连补帧逻辑依赖会随重连清空的 PlayerSession

- `JoinRoom` 重连时 `_players[playerId] = new PlayerSession{...}`（[RoomManager.cs#L132-L152](Assets/Scripts/Network/Server/RoomManager.cs#L132-L152)），**新会话的 `Frames`/`PreSnapshotId`/`CurrentFrameIds` 全空**。
- `SendReconnectData` 补帧循环 `for (i = p.PreSnapshotId + 1; p.Frames.ContainsKey(i); ...)` → 空字典 → **一段历史帧都补发不出来**。
- 结论：即使修复根因 1，当前补帧逻辑也补不出任何帧。帧缓存必须移到**房间级**，不随玩家会话重建。

### 根因 3：快照仍由房主客户端发送（TODO P1 未修）

- [GameSync.SyncPlayerAction](Assets/Scripts/GamePlay/GameSync.cs#L262-L266) 仅房主每 300 帧上传一次快照。
- 房主断线 → 快照停更 → 其他人重连拿到的快照越来越旧。
- 方案：快照改由**服务端持有与生成**（决策点 D1）。

### 根因 4：客户端 KCP 消息处理事件订阅泄漏

- [GameClient.SetClientId](Assets/Scripts/Network/Client/GameClient.cs#L91-L102) 每次 TCP 握手都执行 `_kcpClient.OnMessageReceived += ...`，**重连一次就多挂一个 handler**。
- 第二次连接后同一条 KCP 消息被处理 2 次 → 帧数据重复写入 → 世界状态错乱（叠加问题）。

### 根因 5：客户端无断线检测、无自动重连

- `KcpClient.IsConnected` 只是 `_isRunning` 标志，服务器死后 UI 永远显示"已连接"，心跳静默失败（TODO P1 已记录）。
- 无心跳超时（客户端侧）判定，无重连状态机。

### 根因 6：消息回调跨线程 + 服务端广播线程竞态

- `KcpClient.ReceiveAsync`（后台线程）→ `Input → TryReceive → OnMessageReceived → GameSync.ReceiveSnapshotMessage → AddPlayer → Object.Instantiate` 存在**非主线程调 Unity API** 风险；且与主线程 Timer 的 `TryReceive` **双路径并发触发回调**。
- 服务端 `BroadcastGameSync` 跑在 `System.Timers.Timer` 后台线程（[RoomManager.cs#L90-L92](Assets/Scripts/Network/Server/RoomManager.cs#L90-L92)），与 KCP 接收线程**无锁并发访问** `_players`/`Frames`/`InputQueue`。

## 三、目标架构

沿用 [重构方案.md](重构方案.md) 的整体设计，补充断线重连所需细节：

```
客户端:
  NetworkClient (子系统, 替代 GameClient 内部结构)
    ├── INetworkTransport
    │     ├── TcpTransport   (重构自 TcpSocket: async/await + 异常保护 + IDisposable)
    │     └── KcpTransport   (重构自 KcpClient: 统一会话管理 + 断线检测)
    ├── MessageBus           (线程安全: 网络线程入队, 主线程 Update 消费派发)
    └── ConnectionState      (断线检测 + 自动重连状态机)

服务端:
  GameServer (SubSystemBase)
    ├── ServerNetworkDispatcher   (客户端身份管理, 修复 DeleteClient 重入/UDP重绑)
    ├── RoomManager               (房间级帧缓存 + 服务端快照 + 补帧)
    └── 广播驱动改为主线程 (GameServer.Update) 或加锁, 消除线程竞态
```

### 断线重连时序（修复后）

```
网络瞬断/客户端重启:
  1. 客户端检测到断线 (收包超时/KCP错误/TCP断开) → 双通道状态同步更新, UI 显示已断线, Debug.Log/消息面板输出
  2. 用户手动点击重连 → 重新 TCP 连接 → 服务端分配新 clientId → 握手
  3. 客户端立即发送 KCP 注册包(心跳), 服务端创建新 conv 会话  ← 修复根因1
  4. 客户端按 Name 重新 JoinRoom → 服务端识别为重连
  5. 服务端发送: 当前权威快照 + [快照帧+1, 当前帧] 全量历史帧   ← 修复根因2/3
  6. 客户端: 清空本地状态 → 按快照重建实体 → 帧缓冲灌入补帧 → 恢复正常执行

中途加入（游戏进行中）:
  与服务端重连时序 3~6 相同（按 Name 加入 → 补发快照+历史帧 → 客户端 StartGame 重建），
  区别仅是客户端此前未在游戏中；Lockstep 需保证新玩家加入后立即开始提交输入，否则全房间卡住。
```

## 四、执行计划（分阶段）

### 阶段 A：断线重连修复（核心，先做）

| 步骤 | 内容 | 验收标准 |
|---|---|---|
| A1 | 服务端：客户端 JoinRoom 时**预创建/注册 KCP conv 会话**，或客户端握手后**立即发送 KCP 注册心跳** | 重连后服务端能立即向新 conv 发送快照，不再"未知conv" |
| A2 | 服务端：帧缓存上移到**房间级** `Dictionary<uint 玩家, SortedDictionary<ulong帧, PlayerSync>>`，不随 PlayerSession 重建 | 重连能补发 [快照帧+1, 当前帧] 全部历史帧 |
| A3 | 服务端：快照改为**服务端持有**，由在线客户端定时上报刷新（决策点 D1） | 任意玩家（含房主）断线，快照仍可用 |
| A4 | 客户端：KCP 事件订阅改为**只注册一次**（移除 `+=` 泄漏） | 重连后消息只处理一次 |
| A5 | 客户端：断线检测（收包超时）+ **手动重连**（按钮触发）+ 双通道状态一致性（TCP/KCP 状态联动更新，全部输出 Debug.Log 与消息面板） | 服务器关闭后 UI 立即显示断线；TCP/KCP 状态始终一致；手动重连可用 |
| A6 | 客户端：重连恢复逻辑（清空 `_pendingPlayerNames`/`_players`/`_sendSeq` 按快照重建） | 重连后游戏状态与服务器一致 |
| A7 | 服务端：心跳超时配置生效 + 广播/接收线程竞态修复 | 配置可调；无并发异常 |
| A8 | **中途加入**：服务端对"游戏运行中"新加入玩家也补发快照+历史帧；客户端收到后 StartGame 重建并立即开始提交输入 | 游戏进行中新玩家可加入并恢复状态，不卡住其他人 |

## 五、设计决策（已确认并落地）

| 决策点 | 选项 | 建议 |
|---|---|---|
| D1 快照权威来源 | A. 任一台在线客户端定时上报（现状改造，简单）<br>B. 服务端用确定性模拟自行生成（准确，但工作量大） | **A（已落地）**。项目规模下客户端确定性一致，任一台在线客户端上报即可，服务端仅缓存 |
| D2 重连方式 | A. 自动重连（指数退避）<br>B. 手动点按钮重连 | **B（已落地）**。断线后 UI 提示，用户手动重连 |
| D3 服务端广播驱动 | A. 主线程 GameServer.Update 驱动（简单，无锁）<br>B. 后台定时器 + 全链路锁（保留现有结构） | **A（已落地）**。服务端在 Unity 进程内，主线程驱动最简 |
| D4 重连身份识别 | A. 按 Name 匹配（现状）<br>B. 引入 session token | **A**。保持简单，Name 唯一即可 |
| D5 断线判定标准 | A. 客户端侧"收包超时"（如 3s 未收到任何服务端消息）<br>B. 仅依赖 TCP 断开事件 | **A（已落地）**。TCP 对瞬断不敏感，收包超时最可靠 |
| D6 帧缓存保留量 | 如最近 600 帧（20s，两倍快照间隔）| 超出即淘汰，防内存增长 |
| D7 连接状态一致性 | TCP 与 KCP 双通道统一维护一个 ConnectionState，任一通道断开即整体置为断线，恢复需双通道均就绪 | **已落地**。避免"TCP 断了 UDP 还显示连着"或反向；状态变化必打日志与消息 |

## 六、风险与影响

3. **验证方式**：双开 Unity 客户端 + 开发模式内嵌服务器，模拟：① 断网重连 ② 杀进程重启客户端 ③ 房主断线 ④ 服务器关闭后重启。
4. **文档同步**：本方案落地后同步更新 TODO.md 阶段状态。
