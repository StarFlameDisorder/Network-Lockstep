# Factory 重构方案

> **项目方向**：RTS 帧同步联机（非 TPS 状态同步）。当前 Lockstep + FixedPoint 定点数架构天然适配 RTS。
>
> **当前最高优先级目标**：立即废弃 C++/Qt 服务端，将全部精力集中在 C# 统一技术栈上。C++ 服务端是当前开发速度的最大瓶颈，详见 [1.8 节](#18-c服务端是当前最大瓶颈)。

## 一、当前架构问题

### 1.1 层间耦合混乱

当前依赖关系呈平铺耦合，各层互相直接调用：

```
PlayerController ──→ GameSync ──→ NetworkManager
     │                   │              │
     │                   ↓              ↓
     │              StatusPanel    TcpSocket/UdpSocket
     │                   │         MessageDispatcher
     └───────────────────┘
```

**核心问题：**
- **三层未分离** — GamePlay / Network / UI 之间无接口隔离，互相直接调用
- **跨层调用无事件机制** — 网络数据到达 → 触发游戏逻辑 → 更新 UI，全部是直接方法调用 + 单例访问

### 1.2 单例模式滥用

- `GameSync.Instance` — 帧同步控制器全局单例
- `NetworkManager.Instance` — 网络管理器全局单例
- `StatusPanel.Instance` — UI 面板全局单例

多个全局单例散落各处，导致：
- 模块间紧耦合，无法单元测试
- 依赖关系不透明，谁依赖谁都看不出来
- 生命周期无法集中管理

### 1.3 GameSync 上帝类

`GameSync` 同时承担以下 6+ 项职责，远超一个类的合理范围：

| 职责 | 说明 |
|---|---|
| 网络消息注册与接收 | `RegisterHandler`、`ReceiveMessage`、`ReceiveSnapshotMessage` |
| 房间管理 | `JoinRoom`、`LeaveRoom`、`StartRoom`、`AddPlayer` |
| 帧同步主控 | `SyncPlayerAction`、`PlayerAction`、`UpdateGame` |
| 快照生成与发送 | `SyncSnapshot`、`GetSnapshotSync`、`SetSnapshotSync` |
| 心跳发送 | `HeartBeat` |
| 游戏状态生命周期 | `StartGame`、`PauseGame`、`ContinueGame`、`EndGame` |
| UI 状态更新 | 直接调用 `StatusPanel.Instance` |

### 1.4 Player 实体与表现耦合

`Player` 类同时包含：
- 逻辑数据（位置、速度、帧缓存）
- 表现层操作（直接修改 `GameObject.transform`）

导致逻辑不可独立测试，且帧同步确定性计算与渲染帧耦合。

### 1.5 网络层线程安全缺失

- `MessageDispatcher` — 多线程读写 `_handlers` 字典无锁
- `UdpSocket` — `_pendingPackets`、`_receiveBuf` 在多线程环境下无同步
- `TcpSocket` — 使用 `async void`，未捕获异常直接崩溃

### 1.6 配置硬编码

幻数散落在代码中：

| 参数 | 值 | 位置 |
|---|---|---|
| `BufferSize` | 3 | GameSync.cs / Player.cs |
| `MaxCatchupTime` | 5 | GameSync.cs / Player.cs |
| `_gameFrameRate` | 30 | GameSync.cs |
| `_snapshotSpacing` | 10 | GameSync.cs |
| UDP 缓冲区大小 | 600 字节 | UdpSocket.cs |
| TCP 缓冲区大小 | 2048 字节 | TcpSocket.cs |

### 1.7 其他代码质量问题

| 问题 | 严重程度 | 位置 |
|---|---|---|
| `async void` 模式，异常无保护 | 必须改 | TcpSocket.cs, UdpSocket.cs |
| 字典重复 Key 无保护 | 推荐改 | Player.cs `AddSyncMessage` |
| Socket 操作无 try-catch | 推荐改 | TcpSocket.cs, UdpSocket.cs |
| `IDisposable` 模式缺失 | 推荐改 | TcpSocket.cs, UdpSocket.cs |
| 重连状态重置不完整 | 推荐改 | UdpSocket.cs `CloseLink` |
| 死代码（空方法、注释日志、未用字段） | 推荐改 | 多个文件 |
| 拼写错误 `_playerSyncMessgae` | 可选改 | Player.cs |
| 枚举命名不一致 `Notstarted` / `Pause` | 可选改 | GameSync.cs |
| 字段命名风格不统一 | 可选改 | NetworkManager.cs |

### 1.8 C++服务端是当前最大瓶颈 **[必须改]**

当前服务端为 C++/Qt 独立进程（`Server/` 目录），使用 CMake + Qt + Protobuf-C++ 技术栈。**这已经严重拖累了整个项目的开发速度。**

#### 具体代价分析

| 问题 | 代价 |
|---|---|
| **双语言双编译链** | 每次修改 `.proto` 消息定义，需要分别生成 C# 和 C++ 两套代码，C++ 侧还需要重新 CMake 编译 |
| **跨进程调试地狱** | 调试流程：改 C++ → CMake 编译 → 启动服务端进程 → 启动 Unity → 连接测试 → 两边同时下断点。任何一个环节出错都是时间黑洞 |
| **上下文切换成本** | 在 C#（Unity）和 C++（服务端）之间频繁切换，IDE、语法、调试器、内存模型完全不同，认知负担极大 |
| **Protobuf C++ 运维负担** | `Server/protobuf/include/google/protobuf/` 携带了完整的 protobuf C++ 源码，需要与 C# 侧版本保持一致 |
| **无单进程开发模式** | C++ 服务端是独立进程，无法享受 Unity Editor 内一键 Play 即可同时启动客户端和服务端的便利 |
| **Qt 依赖无意义** | 服务端是 headless 进程，Qt 库完全用不上，却增加了编译依赖和部署体积 |

#### 结论

**立即冻结 `Server/` 目录，不再向 C++ 服务端投入任何精力。** 将服务端迁移到 C# SubSystemBase 从"第三步"**提升为最高优先级**，因为：

1. **没有可运行的服务端，客户端网络重构无法验证** — 改了 TCP/UDP 传输层没有对端测试，等于盲改
2. **C# 服务端可以直接复用客户端网络基础设施** — TcpListener/UdpClient 是 .NET 原生 API，比 C++ socket 编程简洁得多
3. **共享 Protobuf 消息定义** — 未来改消息只需改 `.proto`，C# 代码自动生成，客户端和服务端天然同步
4. **单进程开发模式** — GameServer 作为 SubSystemBase 与客户端同进程运行，Unity Editor 一键 Play 就能联调

## 二、目标架构

### 2.1 分层设计

```
┌────────────────────────────────────────────────┐
│              GamePlay Layer                    │
│   FrameSyncController  GameStateMachine        │
│   PlayerEntity(纯逻辑)  RoomSession             │
│   HeartBeatService     SnapshotService          │
│         ↑ (通过接口 / 事件)                       │
├────────────────────────────────────────────────┤
│              Network Layer (核心)                │
│   INetworkService                              │
│   ├── NetworkClient (客户端)                    │
│   │   ├── INetworkTransport (TCP/KCP 抽象)     │
│   │   └── MessageBus (线程安全消息总线)          │
│   ├── GameServer (服务端子系统中立，独立线程)      │
│   │   ├── ServerNetworkDispatcher              │
│   │   ├── RoomManager                          │
│   │   └── ServerConfig                         │
│   └── NetworkConfig                            │
└────────────────────────────────────────────────┘
         ↑ (配置注入)
┌─────────────────┐
│  GameConfigSO    │
│  ScriptableObject│
└─────────────────┘
```

### 2.2 核心设计决策：Global + GameCore

采用 **Global 静态门面 + GameCore MonoBehaviour 运行时容器** 的组合方案：

```csharp
// 纯静态门面，基础设施入口
public static class Global
{
    public static GameCore Core { get; internal set; }
}

// MonoBehaviour 运行时容器，持有所有子系统
public class GameCore : MonoBehaviour
{
    void Awake()
    {
        Global.Core = this;
        DontDestroyOnLoad(gameObject);
        // 初始化所有子系统
    }

    void OnDestroy()
    {
        // 有序关停所有子系统
        Global.Core = null;
    }

    public INetworkService Network { get; private set; }
    public IGameServer GameServer { get; private set; }     // 服务端子系统
    public IEventBus EventBus { get; private set; }
    public IGameService Game { get; private set; }
    // 其他功能保持现状不动（UI 等），确保能用即可
}
```

**使用约束：**
1. `Global.Core` 中只放接口，不放具体实现类
2. 业务代码优先通过构造函数注入获取依赖，MonoBehaviour 可兜底走 `Global.Core`
3. `Global` 和 `GameCore` 不包含业务逻辑，只做注册、获取、生命周期管理
4. UI、Player 表现层等非网络核心模块**保持现状**，不做大规模解耦，确保功能可用即可

### 2.3 网络相关拆分方案

> 以下为非网络模块声明：**GameSync、Player 等保持现有结构不动**，仅当网络接口变更时做最小适配（替换方法调用）。不做上帝类拆分、不做数据表现分离。

#### 网络层重构（客户端）

```
NetworkManager (当前) → 拆分为:
├── INetworkService         — 网络客户端服务接口
├── NetworkClient           — 客户端网络实现，组合传输通道
├── INetworkTransport       — 传输层抽象接口（支持切换 TCP / KCP）
│   ├── TcpTransport        — TCP 传输（重构 TcpSocket，修复线程安全）
│   ├── KcpTransport        — KCP 传输（预留，后续接入）
│   └── (后续可扩展 WebSocket 等)
├── MessageBus              — 消息总线（替代 MessageDispatcher，线程安全）
└── NetworkConfig           — 网络配置（IP、端口等）

传输层接口定义：
public interface INetworkTransport
{
    ConnectionState State { get; }
    Task ConnectAsync(string host, int port);
    void Disconnect();
    void Send(ArraySegment<byte> data);
    event Action<ArraySegment<byte>> OnDataReceived;
    event Action<ConnectionState> OnStateChanged;
    void Tick(float deltaTime);  // KCP 需要 tick 驱动
    void Dispose();
}
```

#### 服务端迁移（C++/Qt → C# SubSystemBase） **[最高优先级]**

放弃 C++/Qt 独立服务端，将服务端逻辑以 **`SubSystemBase` 子系统** 形式植入 Unity 项目。

**为什么这是最高优先级**：参见 [1.8 C++服务端是当前最大瓶颈](#18-c服务端是当前最大瓶颈)。核心收益：
- **单一技术栈**：只写 C#，IDE、调试器、构建管线全部统一
- **单进程开发**：Unity Editor 一键 Play，客户端 + 服务器同时跑
- **共享 Protobuf**：`.proto` 只生成 C#，客户端和服务端使用同一套消息类
- **C# 比 C++ 的生产力优势**：TcpListener/UdpClient 是 .NET 原生 API，异常安全、内存安全，开发效率远高于 C++ socket 裸写

```
C++/Qt Server → C# SubSystemBase:

GameServer (SubSystemBase)      — 服务器子系统（独立线程）
├── ServerNetworkDispatcher     — 网络分发（移植 NetworkDispatcher）
│   ├── TcpServer               — TCP 服务器（移植 TcpServer.h/.cpp）
│   └── UdpServer               — UDP 服务器（移植 UdpServer.h/.cpp）
├── RoomManager                 — 房间管理（移植 RoomManager.h/.cpp）
│   ├── PlayerSession           — 玩家会话与帧缓存
│   ├── RoomLifecycle           — 房间生命周期
│   └── MatchService            — 匹配服务（2人/4人）
├── ServerConfig                — 服务器配置（端口、房间参数等）
└── Logger                      — 日志服务

与客户端网络层共享 Protobuf 消息定义（C# 已自动生成）
```

**服务端子系统的生命周期与运行模式：**

```
GameServer (SubSystemBase) 生命周期:
  _Init() → 启动独立网络线程，绑定端口，开始监听
  Update() → 驱动 UDP 重传检测 + KCP tick（若启用）
  _Destroy() → 停止线程，关闭所有连接，清理资源

运行模式（通过 ServerConfig 控制）:
  [开发模式] 单进程运行，GameServer 作为子系统与客户端同进程
  [发布模式] 构建为独立 exe，通过 IPC / 独立端口与客户端通信
```

### 2.4 关键变更一览

| 当前 | 重构后 |
|---|---|
| `NetworkManager.Instance` 全局单例 | `INetworkService` 接口注入，纳入子系统管理 |
| `TcpSocket` / `UdpSocket` 硬编码 | `INetworkTransport` 抽象层，可切换 TCP/KCP |
| `MessageDispatcher` 多线程不安全 | `MessageBus` 线程安全消息总线 |
| `async void` 无异常保护 | `async Task` + 异常处理 |
| **C++/Qt 独立服务端进程（开发瓶颈）** | **C# `GameServer` SubSystemBase 嵌入 Unity（最高优先级）** |
| 服务端独立编译环境（CMake+Qt+Protobuf-C++） | Unity C# 统一构建，开发模式单进程运行 |
| 服务端 `UdpServer` 可靠UDP 功能不全 | 移植 + 修复线程安全与重传逻辑 |
| 改 Protobuf 两边各自维护消息代码 | `.proto` 只生成 C#，客户端服务端天然同步 |

> 其他模块（UI、Player 表现层、GameSync 拆分等）**保持现状，仅做必要适配**。

## 三、重构执行计划

> **核心原则**：先有可用的 C# 服务端，再重构客户端网络层。没有服务器对端，客户端网络重构无法验证。
>
> 非网络核心模块（UI、Player 表现、GameSync 帧同步主控等）**保持现状**，仅当网络接口变更时做最小适配。

### 第一步：基础骨架建立

**目标**：让 `Global` + `GameCore` + `SystemManager` 的生命周期可运行。

- 创建 `Global` 静态类 + `GameCore` MonoBehaviour
- 定义核心接口：`INetworkService`、`IGameServer`、`IEventBus`
- 创建 `IEventBus` 实现（事件总线，线程安全）
- 将现有 `SystemManager` + `DataProxyManager` 接入 `GameCore` 生命周期
- **验收标准**：Unity Editor 内 Play，GameCore 正常初始化所有子系统，`Global.Get<T>()` 可获取已注册的子系统

### 第二步：服务端迁移（C++/Qt → C# SubSystemBase） **[最高优先级]** ✅ 已完成代码编写，待联调验证

**为什么提到第二步**：没有可运行的服务端，客户端网络重构无法验证。先把 C# 服务器跑通，形成完整的"客户端 → 服务器 → 客户端"回路。

**策略**：不是逐行翻译 C++ 代码，而是参考 C++ 的协议逻辑，用 C# 惯用方式重写。

- ✅ 创建 `TcpServer`（C# `TcpListener`，线程安全，async/await）
- ✅ 创建 `UdpServer`（C# `UdpClient`，修复可靠UDP：SEQ/ACK + 重传 + 指数退避）
- ✅ 创建 `ServerNetworkDispatcher`（消息路由，替代 C++ `NetworkDispatcher`）
- ✅ 创建 `RoomManager`（房间/玩家会话/帧缓存/心跳/快照）
- ✅ 创建 `GameServer` SubSystemBase，挂载到 `SystemManager`（已注册到 `GameCore.InitSubSystems()`）
  - 支持 `ServerConfig` ScriptableObject 控制：开发模式（同进程） / 发布模式（独立进程）
- ⏳ 使用现有客户端代码（不改动）直连 C# 服务器，验证连通性
- **验收标准**：Unity Editor 一键 Play，客户端连接同进程服务器，能走通 创建房间 → 加入房间 → 开始游戏 → 移动同步 的完整流程

> **C++ 对标参考**（仅参考协议逻辑，不参考代码结构）：

| C++ 文件 | C# 对应 | 说明 |
|---|---|---|
| `TcpServer.h/.cpp` | `Server/TcpServer.cs` | C# `TcpListener` 替代 C++ socket |
| `UdpServer.h/.cpp` | `Server/UdpServer.cs` | C# `UdpClient` 替代，SEQ/ACK 协议逻辑保留 |
| `NetworkDispatcher.h/.cpp` | `Server/ServerNetworkDispatcher.cs` | 消息路由，保留 switch-case 分发逻辑 |
| `RoomManager.h/.cpp` | `Server/RoomManager.cs` | 房间/玩家/帧缓存管理 |
| `GameServer.h/.cpp` | `Server/GameServer.cs` (SubSystemBase) | 服务器入口，生命周期管理 |
| — | `Server/ServerConfig.cs` (ScriptableObject) | 服务器配置（端口/帧率/心跳等） |

### 第三步：客户端网络层重构

**前提**：第二步已经完成，有可工作的 C# 服务器用于验证。

- 定义 `INetworkTransport` 传输层抽象接口
- 创建 `MessageBus`（替代 `MessageDispatcher`，修复线程安全）
- 重构 `TcpSocket` → `TcpTransport`（async/await、IDisposable、异常保护）
- 重构 `UdpSocket` → `UdpTransport`（修复线程安全、缓冲区竞争）
- 创建 `NetworkClient` 统一入口（实现 `INetworkService`）
- 创建 `KcpTransport` 骨架（预留接口，后续实现）
- 将网络客户端作为子系统注册到 `SystemManager`
- **验收标准**：用重构后的客户端连接第二步的 C# 服务器，功能与重构前一致

### 第四步：适配与集成

- 将原有 `NetworkManager.Instance` 调用替换为 `Global.Get<NetworkClient>()`
- 将原有 `MessageDispatcher` 调用替换为 `MessageBus`
- 调整 `GameSync` 等现有代码对接新网络接口（最小改动）
- 删除 `Server/` C++/Qt 目录（确认迁移完整后）
- **验收标准**：所有原有功能在重构后代码上正常运行

### 第五步：KCP 传输层接入（后续阶段）

- 实现 `KcpTransport : INetworkTransport`
- 配置支持 runtime 切换 TCP / KCP
- 与现有 `MessageBus` + 帧同步管道对接
- **验收标准**：弱网环境下切换 KCP，丢包率可接受

## 四、补充说明

### 判断标准：MonoBehaviour vs 普通 C# 类

| 需要 Unity 生命周期/协程/编辑器反射的 | 纯逻辑可独立测试的 |
|---|---|
| GameCore（组合根） | EventBus |
| TcpTransport / UdpTransport | ServerNetworkDispatcher |
| GameServer（服务端子系统中立） | RoomManager |
| TcpServer / UdpServer（服务端） | ServerConfig |
| HeartBeatService | NetworkConfig |
| SnapshotService | PlayerEntity（纯数据） |

### 优化建议分级标准

- **[必须改]**：逻辑错误、安全漏洞、资源泄漏
- **[推荐改]**：低成本、可感知收益的改进
- **[可选改]**：锦上添花，不改无影响

## 五、成熟架构借鉴（Photon Quantum ECS 参考）

> 来源：研究 Photon Quantum 确定性 ECS 框架后提炼的可吸收设计，不引入框架本身。

### 5.1 可吸收设计一览

| 借鉴点 | 对应现状问题 | 优先级 |
|---|---|---|
| **逻辑/表现分离** — System 不碰 GameObject | `Player.UpdateFrame()` 直接改 `transform` | [推荐改] |
| **Frame 上下文对象** — 每帧打包数据传给 System | `GameSync` 散落操作 `_frameId`、`_players` | [推荐改] |
| **输入命令模式** — 帧号在命令创建时敲定 | `PlayerAction` 缓存 `_input` → `SyncPlayerAction` 发送的隐式状态 | [推荐改] |
| **帧缓冲区用有序结构** — 替代 Dictionary | `_playerSyncMessage` 为 `Dictionary` + `ContainsKey` 检查顺序 | [可选改] |

### 5.2 不建议引入

| 模式 | 原因 |
|---|---|
| Quantum 框架本身 | 收费，且与现有 GameCore/SubSystemBase/Protobuf 体系冲突，迁移成本巨大 |
| 全量 ECS | 项目规模不需要，MonoBehaviour 体系够用 |
| 自定义内存分配器 / 指针操作 | C# GC 下收益有限，引入复杂度远超收益 |

### 5.3 落地建议

三条 [推荐改] 合计 < 100 行改动，不碰网络协议不阻塞联调，可在第二步联调过程中顺手做掉：

1. **逻辑/表现分离**：拆出 `PlayerEntity`（纯逻辑）+ `PlayerView`（纯表现），`PlayerView.Update()` 轮询 `PlayerEntity.Position`
2. **Frame 上下文**：引入 `GameFrame` 结构体打包当前帧数据，`UpdateGame()` 变为 `_currentFrame.ApplyAll()`
3. **输入命令**：`FrameInputCommand` 结构体替代 `_input` 隐式缓存，输入一产生就确定帧号
