## 〇、已落地现状（2026-08-02 同步）

```
GameServer (SubSystemBase)                    ← 顶层编排，主线程驱动
  ├── ServerNetworkDispatcher                  ← 消息路由 + 客户端身份（TCP/KCP 双通道统一）
  │     ├── TcpServer                          ← TCP: 仅握手 + 控制消息（JoinRoom/StartRoom 等）
  │     └── KcpServer                          ← KCP(UDP): 帧同步/心跳/快照/补发（可靠有序）
  └── RoomManager                              ← 房间 + 帧同步 + 心跳 + 快照 + 重连 + 中途加入
```

关键变化（相对本文件旧分析）：
- 旧 `UdpServer`（手写 SEQ/ACK/重排序/重传）→ **KcpServer**（`System.Net.Sockets.Kcp`，SimpleSegManager.Kcp），每个客户端一个 conv = clientId
- 帧广播/心跳/保活全部**主线程驱动**（`GameServer.Update` + Dispatcher 统一派发），消除后台线程字典竞态
- KcpSession 加锁（主线程 Timer 与后台 UDP 线程并发串行化）
- 断线重连：KcpServer 待发缓存（conv 未创建时暂存补发）+ 房间级帧缓存 + 补发起点对齐 + 客户端跳帧容错（详见 [全面重构方案.md](全面重构方案.md) 落地记录）
- `ServerConfig` 心跳超时等配置已生效

## 一、当前架构概览

```
GameServer (SubSystemBase)                    ← 顶层编排
  ├── ServerNetworkDispatcher                  ← 消息路由 + 客户端身份
  │     ├── TcpServer                          ← TCP: 黏包处理 + 客户端连接
  │     └── UdpServer                          ← UDP: 手写 SEQ/ACK + 重排序 + 重传
  └── RoomManager                              ← 房间 + 帧同步 + 心跳 + 快照 + 重连

客户端映射（三表）:
  _clientsById[clientId] → ClientState          主表
  _tcpToClientId[TcpClient] → clientId          TCP → clientId
  _udpToClientId[IPEndPoint] → clientId         UDP → clientId
```

事件管线：
```
Client → TcpServer/UdpServer → Dispatcher → RoomManager
RoomManager → (OnSendTcp/OnSendUdp) → Dispatcher → TcpServer/UdpServer → Client
```

## 三、KCP 重写后的目标架构

> **已落地（2026-07-30）**，本节即为当前实际架构。

### 3.1 组件变化

```
现状:                                     KCP方案:
TcpServer ──→ 控制消息(可靠)              KcpServer ──→ 所有消息(可靠有序)
UdpServer ──→ 游戏同步(手工可靠)    →     基于 UdpClient，每个客户端一个 KCP conversation
UdpServer ──→ 心跳                        同一个 conv 多路复用

可以砍掉:
  ✗ TcpServer.cs           ← KCP 提供可靠通道，不再需要 TCP
  ✗ UdpServer.cs 的        ← SEQ/ACK/重排序/重传全部由 KCP 内置
    SEQ/ACK/重传逻辑
  ✗ _tcpToClientId         ← 只剩 conv→clientId 单映射
    _udpToClientId

必须保留:
  ✓ RoomManager 核心       ← 房间生命周期、帧同步模型、快照、玩家会话
  ✓ GameServer             ← 顶层编排
  ✓ ServerConfig           ← 扩展 KCP 参数(nodelay/interval/resend/nc等)
  ✓ 严格锁步模型            ← 不变：等所有在线玩家输入 → 分配帧号 → 广播
```

> 实际落地：TCP 仍保留用于**握手 + 控制消息**（JoinRoom/StartRoom 等），
> 帧同步/心跳/快照/补发走 KCP；KCP 会话在客户端握手拿到 clientId 后立即发注册包创建。

### 3.2 简化后架构

```
GameServer (SubSystemBase)
  ├── KcpNetworkDispatcher                    ← 简化版，单一传输出口
  │     └── KcpServer                          ← KCP 封装层(UdpClient + ikcp)
  │           └── 每个客户端 = 一个 conv id = clientId
  └── RoomManager                              ← 核心逻辑不变

客户端侧:
  KcpTransport : INetworkTransport             ← 已有接口预留
    └── KcpClient (UdpClient + ikcp)
```

### 3.3 设计决策（待确认）

| 决策点 | 选项A | 选项B | 建议 |
|---|---|---|---|
| 单conv vs 多conv | 所有消息走同一个conv | 控制/游戏同步分两个conv | **单conv**，KCP内部流控防止互相阻塞 |
| 初始握手 | 纯UDP(先发裸包注册再切KCP) | 保留最小TCP(握手后断开) | **保留最小TCP**，一次握手交换conv id后断开，简单可靠 |
| KCP update 循环 | 独立定时器(10ms) | 挂在帧广播定时器 | **独立10ms定时器**，KCP需要比游戏帧率更快的update |
| 心跳 | 仅应用层心跳(RoomManager) | 应用层+KCP层双层心跳 | **应用层心跳保留在RoomManager**，KCP自带的心跳作为辅助 |
